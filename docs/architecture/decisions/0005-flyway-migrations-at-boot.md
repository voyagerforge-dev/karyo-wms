# ADR 0005: Flyway migrates the schema at boot, in per-module version bands, out of order

**Status:** Accepted

## Context

Every module keeps its tables in the one `karyo` schema
([ADR 0004](0004-one-postgresql-database-and-schema.md)) and changes its own tables as it changes.
The schema has to be reproducible from nothing, versioned alongside the code that expects it, and
changed forward only. The supported deployment is one application container
([ADR 0022](0022-compose-four-container-deployment.md)).

## Decision

- Flyway, through `quarkus-flyway`, runs inside the application at startup (`migrate-at-start:
  true`) and creates the `karyo` schema if it is absent
  (`services/karyo-app/src/main/resources/application.yaml:30-35`).
- Every migration lives in the aggregator, under
  `services/karyo-app/src/main/resources/db/migration/<module>/`, and Flyway reads exactly the
  seventeen directories listed in `quarkus.flyway.locations` (`application.yaml:40`). Migrations are
  plain SQL.
- One Flyway history covers every module, so a version number is unique across the whole schema
  (`application.yaml:30`). Each module owns a numeric band:

  | Band | Module | Band | Module |
  |---|---|---|---|
  | V1-V2 | common | V901 | webhooks |
  | V101-V111 | inventory | V1001-V1006 | reporting |
  | V201-V207 | product | V1101-V1104 | monitors |
  | V301-V318 | layout | V1201-V1203 | auth |
  | V401-V431 | orders | V1300 | crossdock |
  | V501-V508 | tasks | V1301-V1302 | docstore |
  | V601-V613 | fulfillment | V1400-V1402 | wave |
  | V701-V704 | stocktaking | V1500 | streaming |
  | V801 | work | | |

- `out-of-order: true` (`application.yaml:36-39`), because the bands interleave: a module's next
  migration is usually numbered below versions that other modules have already applied to a
  long-lived database. Within a band, versions stay in order.
- A released migration is immutable, comments included. Flyway validates the checksum of every
  applied migration when it migrates, so editing an applied file stops every existing installation
  at boot. A change is a new forward migration. A decision that has to stay correctable is recorded
  in code, not in a migration comment (`KpiViewRepository.kt:26`).

## Consequences

- The schema is versioned with the code, and a fresh database reaches the current schema by
  replaying every migration.
- Installing or upgrading needs no separate step: starting the new image migrates the database.
- A failed migration fails startup, and there is no rollback. The fix is a further migration.
- A migration directory missing from `quarkus.flyway.locations` never runs, and nothing warns.
- With out-of-order application, a long-lived database can apply migrations in a different order
  from a fresh one, so a migration must not depend on another module's later migration having run.
- This record is the band allocation; no other document holds it. **Known latent defect:**
  crossdock holds `V1300` and docstore already holds `V1301` and `V1302`, so the next crossdock
  migration numbered by the obvious convention collides with an applied docstore version and fails
  startup on every installation. Nothing breaks until that migration is written.
- The migrations of four commercial engines - monitors, crossdock, wave and streaming - are in this
  repository and on the location list, so every installation, free or not, creates their tables and
  leaves them empty ([ADR 0020](0020-free-and-commercial-boundary-per-module.md)).
- Two identity idioms coexist in the schema, `BIGSERIAL` and `GENERATED BY DEFAULT AS IDENTITY`.
  Both satisfy the entities' identity generation, so the mix is cosmetic.

## Alternatives considered

- **A separate migration step that runs before the application starts.** Not taken. It would keep a
  failed migration from taking the application down with it. The reason for migrating inside the
  application instead is not recorded.
- **Independent version numbering per module.** Not possible with one Flyway history over one
  schema; hence the bands.
- **Liquibase.** Rejected: its changeset formats are more verbose and harder to review than SQL, and
  a database-agnostic abstraction buys nothing for a PostgreSQL-only product while hiding
  PostgreSQL features such as partial indexes.
- **Hibernate schema auto-update.** Rejected: it cannot drop anything, cannot create indexes or
  constraints the entities do not map, keeps no version history and is unsafe in production.
- **Hand-applied SQL scripts.** Rejected: no record of what has run, no ordering and no checksums.
